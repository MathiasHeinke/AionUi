## 1. Findings

### P1-1 — Legacy-record "write-on-read" migration funnels previously-safe reads through a non-fsync rename; a crash window can destroy a PAID image artifact record

- FACT(packages/desktop/src/process/commandEve/imageArtifactStore.ts:100-106): the store's local `writeJsonAtomic` writes a temp file and `renameSync`s it **without any `fsync`** of file or directory.
- FACT(packages/desktop/src/process/commandEve/imageArtifactStore.ts:137-172): new in this RC, `readStagedHandleFile` and `readManagedImageRecordFile` REWRITE the record via that `writeJsonAtomic` whenever a legacy record lacks `seat_id` (`if (seatMissing) writeJsonAtomic(file, staged)` at :147 and :169). These run on ordinary read paths — record lookup (:204), purge scans (:256), pending counts (:315).
- Contrast — FACT(packages/desktop/src/process/services/project-workspace/storage/atomicJson.ts:62-87): the project-workspace store's `writeFileAtomic` fsyncs the temp descriptor before rename and fsyncs the directory after; the office lane additionally uses create-only publication with full read-back verification (FACT privateDocumentCache.ts:195-220). The image lane has neither.

Failure path (the brief's "abort BETWEEN write and rename", shifted one step later): (1) user upgrades from a pre-seat build holding paid, ACTIVE managed image records without `seat_id`; (2) any list/preview/reconcile read triggers the in-place rewrite; (3) power loss lands after the rename is journalled but before data blocks flush — the classic zero-length-after-rename window; (4) on next boot the record JSON is empty, `parseManagedImageArtifactRecord` fails, and the paid artifact silently reads as absent (FACT imageArtifactStore.ts:159-172 — unreadable reads as `undefined`); the blob bytes are orphaned. Before this RC, reading a legacy record was a pure read and could not lose it.

Why it matters: probability is low (crash inside a narrow window), but the asset is a paid artifact, the trigger is a routine read, and the same file previously carried zero write risk. INFERENCE(imageArtifactStore.ts:100-106): routing these rewrites through the fsync-ing `writeFileAtomic` from `atomicJson.ts`, or simply tolerating the missing `seat_id` in memory without rewriting, removes the entire window.

### P1-2 — Office operations pending at Main exit are permanently orphaned: the result the user paid attention for never becomes an artifact, and no operator path recovers it

- FACT(packages/desktop/src/process/commandEve/document/officeArtifactLineageMain.ts:260-266): `operationBelongsToActiveGeneration` requires `operation.process_id === active.processId && operation.process_nonce_sha256 === active.processNonce && operation.seat_context_revision === active.seatRevision`. The process nonce is a fresh random per boot (FACT atomicJson.ts:10-13 `PROCESS_BOOT_NONCE_SHA256`), and the code comment states the intent: "pending work survives renderer reloads but never an unverifiable Main restart."
- FACT(officeArtifactLineageMain.ts:576-599): the reconcile filters ALL operations through that predicate before matching transcript candidates; a pre-restart pending operation is filtered out on every future run.
- FACT(conversationArtifactStore.ts): the store exposes `createOfficeOperation`, `readOfficeOperation`, `listOfficeOperations`, and completion create/read — no delete or prune for operation records exists anywhere in the diff or the current file (searched; none found).

Failure path: (1) user sends "make me a Word doc" — `beginCommandEveOfficeArtifactOperation` durably records the operation (officeArtifactLineageMain.ts:144-158) and the turn dispatches; (2) Hermes writes the .docx into the conversation workspace and emits its media directive into the transcript; (3) the app quits or crashes before any artifacts-list/reconcile pass runs; (4) after restart, every reconcile skips the operation forever — the document never enters the artifact registry, never appears in the conversation's artifact list (office listing only serves operation-completed lineage, FACT officeArtifactLineageMain.ts:779-794), and can never be an edit parent. The bytes still exist as a loose file in the workspace, so this is loss of the product artifact and its lineage, not of the data — which is why this is P1, not P0. Secondary: the orphaned operation record (and one created then abandoned when the seat changes right after create, FACT :159 — refusal AFTER `createOfficeOperation` at :144 with no compensating delete) accumulates without bound; stale records are well-formed, so they don't poison listing, they just never die.

Why it matters: the durable-receipt machinery is exemplary (see §"What holds"), but its restart story is deliberately fail-closed with no recovery affordance and no user-visible message — the user's document just never shows up. If the trade is intended, it needs at minimum a surfaced notice and a GC for dead operations.

### P2-1 — Seat-isolation asymmetry: the video lane and the Office conversation-authority check do not verify conversation↔seat ownership, while the image lane now does

- FACT(packages/desktop/src/common/config/eveArtifactCapabilityHandleCore.ts:82-86): the grant type splits deliberately — `video_edit` grants carry `seat_id?: never` ("Video grants remain byte-compatible; only image_edit authority is Seat-owned").
- FACT(packages/desktop/src/process/bridge/commandEveVideoBridge.ts:1683): `handleCommandEveVideoEdit` reads the grant with NO seat expectation; every subsequent fence (conversation deny :1709-1717, permit conversation fence :1770, consume :1877) is conversation-scoped, not seat-scoped.
- FACT(commandEveVideoBridge.ts:692-704): `handleCommandEveVideoArtifactsList` serves any `conversationId` from the shared `getDataPath()` store with no seat check at all (the office records merged into the same reply DO pass a seat/authority fence — officeArtifactLineageMain.ts:770-775).
- FACT(packages/desktop/src/process/commandEve/officeArtifactAttachmentCore.ts:414-434): `resolveCommandEveOfficeConversationAuthority` resolves ANY conversation id against the single install-global backend (`getBackendPort` reads one global `__backendPort`, FACT :127) and captures whichever seat is ACTIVE — it verifies the seat didn't change during the fetch, never that the conversation belongs to that seat.

Attack path (cross-seat read, not spend): seat B's renderer (or any code speaking the IPC bridge) calls `command-eve.video-artifacts-list` with a conversation id created under seat A; the reply contains seat A's video artifact records including local `payload.path` values. Similarly, the office lane will happily ADOPT a document out of seat A's conversation workspace into seat B's artifact registry, because authority is "active seat + conversation exists", not ownership. Spend remains fenced (a permit must be minted by the composer inside that conversation), and per-store office/image records are seat-partitioned — so this is exposure/adoption, not billing.

Grading note: the video-lane seatlessness is pre-existing and explicitly kept byte-compatible in this RC (FACT commandEveVideoBridge.ts:756-757 comment "The video lane's seatless index remains unchanged"); the office authority shape is new but store-partitioned per seat. HYPOTHESIS(no evidence): whether a real seat B UI can obtain seat A conversation ids depends on backend conversation-list scoping, which I did not trace into AionCore. Settling it needs a read of the backend `/api/conversations` handler's seat filtering. Until then this is a defense-in-depth gap, P2 — but it is the release's clearest inconsistency: the same tenant-separation argument that justified seat-fencing images applies verbatim to clips.

### P2-2 — A completed PAID image generation can be discarded post-hoc by the seat-epoch fence; the "resend" it requests is a second spend

- FACT(packages/desktop/src/process/bridge/commandEveImageArtifactBridge.ts:749-756): after `coordinator.run` resolves, a final `capturedSeatEpochIsActive()` check converts even a SUCCESSFUL result into `image-generate-seat-changed` with `artifactState: 'stored_not_bound'` and `retryable: true`.

Failure path: (1) generation succeeds and is debited at the gateway; (2) the user switches seats (or a seat-context revision bump lands) in the window between the coordinator resolving and this check; (3) the paid, staged artifact is withheld and the user is told to resend; (4) a resend is a NEW `requestId` → a new debit for a new generation. The first artifact is only recoverable if its bind candidate reaches the transcript reconcile under the original seat (FACT imageArtifactReconcileMain.ts:87-104 — reconcile is seat-scoped and can still bind it later), which is not guaranteed for the renderer-initiated path. INFERENCE(commandEveImageArtifactBridge.ts:383-391): the replay cache cannot rescue this either, because the completed-cache identity includes `seatContextRevision`, so the post-switch resend never matches. Deliberately fail-closed toward tenant separation — correct priority — but it converts a narrow race into a quiet double payment for one desired image. Bounded, needs a UX/receipt answer rather than a fence change.

### P2-3 — One damaged record file hides EVERY office artifact of its conversation, silently

- FACT(conversationArtifactStore.ts `listOfficeArtifacts`): the listing THROWS `workspace.journal-corrupt` if ANY `.json` entry in the conversation directory fails the immutable-read checks — including `nlink !== 1`, mid-read mtime change, or any `kind: 'file'` record that fails parsing (`readImmutableOfficeRecordText` requires `nlink === 1` and three-way stat identity).
- FACT(officeArtifactLineageMain.ts:777-797): `listCommandEveOfficeArtifactRecords` catches everything and returns `[]`.

Failure path: a backup tool hardlinks one artifact JSON (nlink→2), or one file is truncated by P1-1-class interference → the office half of the artifact list for that conversation becomes permanently empty, with only a `console.warn` on the video-list channel (commandEveVideoBridge.ts:697-701). Fail-closed is the right default for lineage authority; the blast radius (whole conversation, indefinitely, no surfaced error, no quarantine of the single bad file) is the finding.

## What holds (verified, load-bearing, and worth stating)

- **Seat fencing of the managed image lane is real and consistent.** Every read that can return bytes or authority now demands an expected seat and compares record-side: `readImageArtifactRecordById` (imageArtifactStore.ts:193-206), `readImageArtifactBytes` refuses unless the record check passes first (:217-222), staged-handle resolution (:184-191), bind (:454-459 seat-mismatch), list (:515-521), preview (commandEveImageArtifactBridge.ts:879-881), and edit — where the grant is seat-checked twice, once inside `readArtifactCapabilityGrant` and once explicitly (`grant.seat_id !== capturedSeatId` at commandEveImageArtifactBridge.ts:1188, refusing with the indistinguishable `handle-unknown`).
- **The coalescing key question from the brief has a good answer.** The generate coordinator keys BOTH the request-replay map and the per-conversation in-flight map on `{seatId, seatContextRevision, requestId|conversationId}` (FACT commandEveImageArtifactBridge.ts:383-391), and the request digest itself now folds in the captured seat epoch (:567-580). Seat B cannot join seat A's in-flight generation or replay its completed result.
- **Derived artifacts inherit correctly.** A staged child with `parent_artifact_id` binds only if the parent is ACTIVE, same conversation, and same expected seat (FACT imageArtifactStore.ts:470-474 `parent-mismatch`); the child record itself is stamped with the CAPTURED seat at stage time (`stageGeneratedImageArtifact` requires and stamps `capturedSeatId`, :354, :370), never the binder's word.
- **Legacy import is fail-closed onto seat-1 as claimed.** `importLegacyImageArtifact` refuses any caller whose captured seat is not exactly `LEGACY_SEAT_ID` (FACT imageArtifactStore.ts:608-611) — a non-legacy seat cannot adopt pre-seat bytes.
- **Paid video edit target is now exact, not guessed.** The clarify card resolves ONLY the artifact named by the Main-injected `[command_eve:artifact_target:<id>]` prefix (FACT composerArtifactReferenceCore.ts:153-163; MessageAcpClarify.tsx — `artifacts.find(candidate => candidate.id === followupTarget.artifactId)`, accept button disabled when unresolved), replacing the previous newest-matching-artifact selection that the base commit still contained (verified in the diff: the `newest`/`createdAt` loop was removed). Acceptance replays through the composer with the exact reference (`AcpSendBox.tsx:2612-2658`), and the mint-time hash binding in Main (`resolveVideoEditCapability` → `resolveArtifactCapabilityGrant` with observed bytes hash) makes a post-confirmation artifact swap a refusal, not a mistargeted spend.
- **Double-charge on duplicate delivery is structurally handled.** Video-edit request ids are content-derived (FACT commandEveVideoBridge.ts:1898-1901), image-edit request ids likewise (FACT commandEveImageArtifactBridge.ts:1346-1349), permits are consumed by exclusive create before the provider call (videoBridge:1870-1892), and the gateway side of the contract is now pinned by new tests: "dual video edit arrivals apply one debit and make one provider call" (FACT supabase/functions/eve-multimodal/index.test.ts, added in this RC; `supabase/functions/eve-multimodal/index.ts` itself is byte-identical to base — verified empty diff). A permit presented in a foreign conversation is refused record-against-record (videoBridge:1770).
- **Credit pool (brief item c).** All lanes authenticate spends with the ONE license wire read from the shared `dataPath` (FACT commandEveVideoBridge.ts:1815 `readLicenseWire(dataPath)`), so all seats of an install debit one account pool by construction; `seat_id` rides only as attribution metadata and is dropped if malformed (FACT eveMultimodalGatewayCore.ts:32-36). No local path can split or re-aim the pool; misattribution worst case is a wrong metadata label, never a wrong account. Cross-account behavior lives in the unchanged gateway (not re-audited beyond the new tests).
- **Office durability primitives are the strongest in the codebase.** Create-only publication with fsync'd directory chains and full read-back verification (privateDocumentCache.ts:195-220, conversationArtifactStore.ts `publishOfficeRecordOnce`), completion receipts that must match the EXACT sorted artifact membership (`completedOfficeOperationIdsWithExactReceipts` — a partial or forged completion reads as journal corruption, not as done), and lineage verification that re-hashes actual bytes against the manifest before an artifact is served or used as an edit parent (officeArtifactLineageMain.ts:234-248, :744-760). The transcript-supplied source path is fenced by realpath containment inside the conversation workspace, O_NOFOLLOW, nlink===1, size caps, and TOCTOU re-stats (FACT officeArtifactAttachmentCore.ts:349-411).
- **Capability-index split closed a real pre-existing hole.** Image handles moved to a seat-keyed, operation-keyed index (artifactCapabilityHandleStore.ts:194-197, :288-291) and the video reuse path now demands `operation === 'video_edit'` before reusing an index entry (:228) — before this RC both lanes shared one `(conversation, artifact)` index file with no operation check on the video side.

## 2. Independent verdict on 4066ac807 (removal vs restore)

**The removal is correct. I would have made the same call. One residual concern, below, is real but does not change the verdict.**

What I verified, not took on faith:

1. The base RC really was broken exactly as claimed: `2c7d4e754`'s emitted shim contains two calls to `_install_command_eve_acp_session_recovery_patch` plus its EXPECTED-ledger entry and NO definition (FACT — `git show 2c7d4e754:…runtimeBootstrapCore.ts` lines 5551, 9389, 9465; zero `def` for that name). A module-level call to an undefined name is a NameError at import; every provisioned seat loses the provider. The frozen tree contains zero references to the retired name (verified by search).
2. The retired self-heal's actual behavior (FACT — removed lines in `git show 69be16f72`): on a missing session at load/prompt it ADOPTED a fresh agent under the SAME session id, registered it in the manager, persisted it, and let the turn proceed with the prior model context silently gone (one log warning). That is exactly the "silent auto-create onto an identity the product never authenticated" the guard's header names as unsafe (FACT runtimeBootstrapCore.ts:8103-8107) — and the bundled wheel confirms the danger is live upstream: `resume_session` creates a brand-new session when the id is unknown (FACT whl acp_adapter/server.py:1630-1633 "not found, creating new"), and `prompt` answers an unknown session with `PromptResponse(stop_reason="refusal")` (FACT server.py:1806-1807), the misleading path the guard also intercepts.
3. The guard genuinely owns the invariant's full surface, wider than the retired patch did: it wraps `load_session`, `resume_session` AND `_prompt_impl`, restores the silent-`_restore` diagnosis logging, and refuses with an explicit `COMMAND_EVE_ACP_SESSION_UNKNOWN … needs_user` RuntimeError (FACT runtimeBootstrapCore.ts:8108-8131, 9088-9112, 9170-9173). The retired patch wrapped only load and prompt, and never fenced `resume_session` — the one upstream method that actually auto-creates. Restoring the old body would therefore have produced the brief's (e) defect in its purest form: two installed wrappers on the same methods owning contradictory policies (adopt vs refuse), with winner decided by install order.
4. The install-order dependency the guard relies on holds: `_install_command_eve_prompt_admission_patch` recreates the `_prompt_impl` seam that the V22 wheel inlined (FACT runtimeBootstrapCore.ts:6272-6276, wheel has zero `_prompt_impl` occurrences — verified `grep -c` = 0) and runs before the guard in both the retry block and the module tail (FACT :9385-9389, :9448-9463). The new ledger test adds the missing check class — a call that resolves to no definition (FACT tests/unit/command-eve/shimPatchLedger.test.ts header) — which is precisely the class that produced this P0.

**Did the field lose a self-heal it needs?** What is lost: a seat whose durable session row is missing used to keep "working" by silently discarding the conversation's model context. What exists now: the turn fails with an explicit instruction ("start a new chat or reopen a known session"), only the broken conversation is affected, and a NEW chat on the same seat works — so this is not a dead seat and not restart-dependent. That is the right trade for a product that attaches desktop approvals and tool progress to session identity.

Residual concern (P2-class, does not overturn): the guard raises a plain `RuntimeError`, not a typed ACP `SessionNotFound`, from inside `load_session`/`resume_session`/`_prompt_impl`. FACT: no TypeScript code outside the shim and its test references `COMMAND_EVE_ACP_SESSION_UNKNOWN` (repo-wide search), so nothing on the desktop side clears the cached session id or offers a one-click "start new chat" when it fires. HYPOTHESIS(no evidence): how legible the raw error renders in the chat depends on the ACP JSON-RPC error path and AionCore's generic error display, which I did not trace end-to-end; the guard's own header notes AionCore's `rebuild_after_session_not_found` rescue keys on a condition this error does not raise. If field reports show users stuck rereading a German-plus-English RuntimeError, the fix is a desktop-side recognizer for this error string — not a return of the self-heal.

## 4. The single weakest point

**The seat-ownership story is enforced per-lane instead of at one boundary, and the video lane is the lane left out.** The image lane now proves seat ownership at every read, bind, grant, and coalesce key; the office lane partitions its store by seat; the video lane — the one with the longest-standing PAID path — still serves any conversation's artifact records, local file paths included, to whichever seat asks, and mints/honours seatless edit grants (P2-1, FACT commandEveVideoBridge.ts:692-704, :1683; FACT eveArtifactCapabilityHandleCore.ts:82-86). Today the spend itself stays fenced by composer-minted, conversation-bound permits, so I could not build a P0 out of it. But every future feature that reuses "the video lane's seatless index remains unchanged" as precedent widens a gap the rest of this release just spent enormous, well-executed effort closing — and the reseller multi-client scenario that motivated seat isolation (seatConfigKeyCore.ts:14-19, DSGVO framing) applies to a client's generated clips at least as much as to their images and documents. This asymmetry — one invariant, three lanes, two policies — is exactly the dual-ownership failure class this release was supposed to retire.
